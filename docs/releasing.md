# Packaging and release verification

Each harness package owns its version and delivery archive. The root workspace is
private. The current distribution is a local `@camenae/bob` archive; registry
publication is a separate maintainer action, not part of the scripts below.

## Prerequisites

Follow [development setup](../CONTRIBUTING.md), including preparation of the
approved Bob archive. Retain both root `bun.lock` and Bob's `package-lock.json`;
package acceptance and release tooling use npm archive operations.

Run lint, typecheck, both test runners and build before delivery. The build
validates pinned runtime/helper identities, applies dependency-bundle corrections,
rejects non-Node external imports and emits public declarations.

## Validate one exact archive

From the repository root, after the build and checks:

```sh
delivery=$(mktemp -d "$PWD/.delivery-XXXXXX")
(cd packages/bob && npm pack --pack-destination "$delivery")
archive="$delivery/camenae-bob-0.5.0.tgz" # use the package's selected version
bun run smoke:package "$archive"
bun run smoke:package:node "$archive"
sha256sum "$archive"
```

On macOS, use `shasum -a 256` instead of `sha256sum`. `npm pack` runs the package's
prepack build. An explicit archive passed to either smoke is installed unchanged;
it is not repacked. The delivery directory is ignored and must be retained
outside any disposable validation checkout.

Acceptance checks shipped files, exports, consumer TypeScript declarations,
installed permission/gate behavior, real private Bob over native/socket paths,
usage, managed modes, caller-owned workspaces and keyless SSO selection. The
loopback MCP test retains Allow/Ask/Deny, cross-server isolation, unavailable-tool
attempts, native category denial and fresh workers. No paid inference is required.

The MCP fixture supports `--profile=native|socket|all` for sanitized phase timing.
Use the existing `BOB_GATEWAY_TEST_PACKAGE` and `BOB_GATEWAY_TEST_MCP_PACKAGE`
fixture overrides to select installed entrypoints. A filtered profile is not a
substitute for full installed-package acceptance.

## Provenance

Retain the archive and a manifest containing:

- Package name/version, unique archive identity and SHA-256.
- Source commit and dirty state, or a deterministic per-file source digest
  manifest for a new repository without history.
- Runtime compatibility manifest and dependency lockfile identities.
- Platform/toolchain versions, exact checks and their results, and evidence logs.
- Known limitations and any checks not run.

Two builds sharing a package version are not interchangeable. Never overwrite an
accepted archive or claim later source edits were validated in it. Packaging is
not authorization to change a consumer's dependency or deployment.

## Version changes

From `packages/bob/`, `bun run release` offers a version choice and builds a local
archive. It updates package metadata and locks, but does not run tests, commit,
tag or publish. If packaging fails, the chosen version remains changed. Inspect
those edits, rerun the checks and validate the resulting archive before delivery.

## Licensing and public publication

SDK-authored code is MIT licensed. Preserve the package license and
[third-party notices](../packages/bob/THIRD_PARTY.md), including IBM's bundled
licenses and the dependency notices generated by the bundler. The SDK license
does not relicense Bob, its runtime corrections, or upstream dependencies.

Before publicly distributing a Bob-containing archive, confirm your entitlement
and the applicable IBM redistribution/modification terms. Passing technical
checks is not that confirmation. A source-only repository excludes the Bob
archive and generated runtime. Do not add registry/repository URLs until the
actual destinations have been chosen.

## Evidence limits

Current automated acceptance is established on Linux x64 with Bun 1.4.2 and Node
22.18.0; it is not proof at the minimum Node version or on every platform. Native
helpers cover a narrower platform set than TypeScript alone. Interactive Linux
SSO, Windows, remote browser login, exhaustive Office/tool characterization,
durability and deployment containment remain unproven or unsupported. See
[Bob compatibility](../packages/bob/COMPATIBILITY.md).

Paid live checks and updates to running consumers require separate authorization.
